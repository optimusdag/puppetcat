### Bug 3 (root-caused, hardened, uncommitted): EP1 export missing audio after ~8:56
NOT a code bug in the mixing logic - proven by direct reproduction. Root cause: `/Volumes/IntSSD` is an external USB drive; a ~60+ minute continuous render writing there silently truncates the audio file partway (video survives intact) with no error surfaced. Confirmed via a clean controlled test matrix: writes to `/tmp` (internal SSD) never truncated (three separate runs, including the full 25143-frame render); writes to `/Volumes/IntSSD` truncated identically (536.362667s) across independent runs including from a freshly-restarted process with today's code, ruling out stale-process/code-bug theories.
- **Hardening implemented**: `verify_mixed_duration()` in `puppetcat-export/src/lib.rs`, called after `mix_to_file` succeeds and before muxing - compares the mixed file's actual duration against the timeline length (the mix's own filter graph pads/trims to exactly that length via `apad=whole_dur`, so a shorter result means a silent write failure). Now fails loudly instead of shipping a broken file. Test: `verify_mixed_duration_catches_a_short_write`.
- EP1.mp4 was eventually successfully re-exported in full (both video and audio complete) via a direct one-off `render()` call from a test, bypassing the dead MCP connection (see below) - confirmed via ffprobe both streams at 838.1s. That was BEFORE the scratch-dir feature existed, using output directly on the USB drive after the disk had some space freed - it worked that one time, but the underlying USB reliability risk for long renders remains real and motivated the feature below.

### Feature (implemented tonight, uncommitted): "render to a scratch folder, then move" setting
User's explicit ask, directly motivated by bug 3: add an app setting so exports render to a fast/reliable local scratch folder first, then move the finished file to the real destination - avoiding sustained long writes to a slow/unreliable drive.

Implementation (all uncommitted):
- `puppetcat/src/prefs.rs`: added `temp_export_folder: Option<String>` to `Preferences` (serializes as `tempExportFolder` via existing `rename_all = "camelCase"`).
- `puppetcat-export/src/lib.rs`: `ExportRequest` gained `scratch_dir: Option<String>`. `render()` now renders into `scratch_dir` (creating it if needed) when set, producing a `.{stem}.puppetcat-final.mp4` there, then calls new `move_finished_file()` to relocate it to `output` (plain `rename` first, falls back to `copy` + `remove_file` for cross-device moves - `rename(2)` refuses `EXDEV` outright). When `scratch_dir` is `None`, behavior is byte-identical to before (renders straight to `output`, no extra move) - zero risk to the default path.
- `puppetcat-host/src/export.rs`: `ExportSpec` gained `scratch_dir: Option<String>`, threaded into `ExportRequest` in `request()`. Added `pub fn temp_folder_preference(dirs: &AppDirs) -> Option<String>` - a minimal, dependency-free reader that peeks the `tempExportFolder` key straight out of `settings.json` without needing the full `Preferences` type (avoids a circular dependency, since `puppetcat-host` can't depend on the `puppetcat` binary crate). Lets both the GUI and the agent honor the same machine-wide preference.
- `puppetcat-agent/src/engine.rs`: `start_export()` now populates `ExportSpec.scratch_dir` via `puppetcat_host::export::temp_folder_preference(&self.dirs)` - so agent-driven exports (like the MCP tool `start_export`) automatically honor the same setting as the GUI, no new MCP parameter needed.
- `puppetcat/src/studio.rs`: `export_start()` populates `ExportSpec.scratch_dir` from `self.prefs.temp_export_folder` directly (blank string treated as `None`). Also added `temp_export_folder` to the `SettingsData` struct literal in the sync function (~line 4406-4423).
- Settings UI: `puppetcat/ui/dialogs/settings.slint` - new "Exporting" section in the General tab (tab 0), with a `Field` (path, placeholder "Same as the destination") + "Browse" button, following the exact pattern already used in `export.slint`'s destination picker. New callbacks `temp-export-folder-edited(path)` / `temp-export-folder-browse()` on `SettingsDialog`, plus `SettingsData.temp-export-folder: string`.
- `puppetcat/ui/app.slint`: forwarded the two new `SettingsDialog` callbacks up to the top-level `App` component (`settings-temp-export-folder-edited`/`settings-temp-export-folder-browse`) - this forwarding step was easy to miss and caused an initial build error (`no method named on_settings_temp_export_folder_edited`) until added.
- `puppetcat/src/main.rs`: registered `on_settings_temp_export_folder_edited` (writes `state.prefs.temp_export_folder`, treating blank as `None`, saves prefs) and `on_settings_temp_export_folder_browse` (native `rfd::FileDialog::pick_folder()`, same idiom as the existing export-folder browse callback), following the exact pattern of `on_settings_language_changed`.

Tests added (all passing): `render_with_a_scratch_dir_still_lands_at_output` (portable, same-filesystem rename path, verifies scratch dir is created if missing and left empty afterward), `move_finished_file_moves_or_fails_without_losing_data` (rename success + failure-must-not-delete-source contract; a genuine cross-device copy-fallback isn't portably testable in a unit test). Additionally **manually verified against the real hardware** with a one-off ignored test (written, run once showing "stage: moving to destination" and a file landing correctly at a real `/Volumes/IntSSD/...` path from an internal-SSD scratch dir, then deleted before finishing) - proves the exact real-world cross-device scenario this feature targets actually works on this machine.

Full workspace build (`cargo build --workspace`) and full test suite (`cargo test --workspace`) both clean: every crate 0 failures (puppetcat-export 24 tests, plus puppetcat/puppetcat-host/puppetcat-agent/puppetcat-render/puppetcat-media/puppetcat-project/puppetcat-core/puppetcat-effects/puppetcat-speech/puppetcat-text all passing, ~200+ tests total across the workspace).
